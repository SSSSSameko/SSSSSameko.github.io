日期：2026-11-05。审查版本：3.6.3。范围仅限本项目当前工作区，保留接手时的未提交改动。本轮未提交、推送或部署，未修改生产数据、凭据或登录目录。

## 本轮发现与修复

| 问题 | 修复与证据 |
| --- | --- |
| 官方接口把容差内的名单标成完整；总数为 `null` 时被转换成 0，可能第一页就结束 | 数量完整判断独立于补抓容差；未知总数继续按分页结束条件读取。离线服务用例验证 4/5 仍不完整、未知总数跨页取得 201 条、标识不可靠不声明完整、确实取得 200/200 时完整 |
| 官方接口后续页面发生可恢复的上游故障时，前面的名单丢失 | 复用分页异常边界，保留已取得候选及失败页；认证失败与限流仍终止任务。HTTP 502、401、429 场景分别验证 |
| `complete: false` 且总数未知时，前端可能没有任何范围提示 | 名单与开奖确认统一提示实际取得数量、总数未知和完整性未确认；单元测试先失败后通过，并用手机尺寸浏览器核对两个页面 |
| 实际可见条目超过上游旧总数时，开奖记录保存被拒绝 | 允许上游计数滞后或变化，原样保留总数和实际数量；继续拒绝非法计数、原始数小于去重数、重复中奖和奖项人数不一致。真实本地 HTTP 测试验证 2 条候选 / 上游总数 1 可保存 |
| 后台读取记录将未知数量 `null` 转成 0 | 使用明确的数值读取边界，缺失、空值、布尔值不再伪装为数量；验证总数、可抽数及来源数量保持未知 |
| 保存记录缺少名单载入时间，难以区分抓取时间与开奖保存时间 | 持久化并在后台详情返回 `sourceMeta.loadedAt`，与已有 `crawlId` 配合追溯；HTTP 测试验证写入与读取。历史记录不会补造时间 |
| 部署检查未覆盖新补抓模块和后台导出依赖；部分报告仍写临时版本号 | 补全发布文件清单、后台依赖健康检查；同步包版本、README 和唯一更新日志；旧报告明确为归并前的历史证据 |

200 条及以上的大名单正常扫描后允许约 20% 缺口的规则保持不变；明确分页错误不会按容差豁免。容差只决定停止补抓，不承诺补齐不可见条目。默认请求间隔和随机延迟保持 3.6.2 的设置。

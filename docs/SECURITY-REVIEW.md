# 3.4.0 安全与稳定性审查

审查范围包括 React 前端、Node HTTP 服务、管理后台、微博抓取与 Cookie 保活、只读登录态接口、Caddy、systemd、安装脚本和发布流程。未发现 SQL 注入、命令注入、任意文件读取、存储型 XSS 或仓库内明文密钥。

## 3.4.0 的可用性取舍（已知并接受）

以下取舍是为避免正常访客无法使用而做出的，运营者需要了解其边界：

- 服务端配置 `API_KEY` 时，会把密钥注入本站 `config.js`，浏览器端因此不再需要手工填写。代价是任何能加载本站的人都能读到该密钥，`API_KEY` 不再构成强访问控制。真正的边界是 `CORS` 来源白名单、限流、上游反向代理和云防火墙；不要把 `API_KEY` 当作唯一防线。
- 静态托管版本的 HTML meta CSP 把 `connect-src` 放宽到 `https:`，以便把静态前端指向自己的后端。前端仍会用可信地址白名单校验接口地址，服务端托管版仍下发严格 CSP。脚本策略未放宽，仍禁止内联脚本和 `eval`。
- 反馈与抓取任务限流放宽到 10 次/分钟、30 次/天和 4 个并发，并改为按 `IP + 客户端标识` 计数，减少同一 NAT 下的互相误伤；限流仍然生效，只是阈值更高。
- 抓取任务在订阅连接断开后保留 30 秒宽限再取消，用户显式 `DELETE` 仍立即取消。
- 开奖记录默认不再按 180 天自动清理，仍受数量（1000 条）与容量（100 MB）上限约束，后台仍可逐条删除。运营者需要自行制定并披露保存期限。
- 访问密钥保存在浏览器 `localStorage` 以便复用；这与密钥已公开注入 `config.js` 的现状一致，不额外扩大暴露面。

## 只读登录态接口边界

- `GET /v1/cookie/current` 由安装脚本为新部署默认写入 `ENABLE_COOKIE_READ_API=1` 并生成独立密钥；未设置该变量或设为 `0` 时按 404 处理，不泄露接口是否存在。
- 接口只接受独立的 `COOKIE_READ_KEY`，且该密钥必须为 64 位十六进制字符，并与 `API_KEY`、`ADMIN_KEY`、`COOKIE_WRITE_KEY`、`ADMIN_SESSION_SECRET` 均不相同；请求头只认 `x-cookie-read-key` 和 `Authorization: Bearer`，不会回退读取前端共享的 `x-api-key`。
- 未配置 `COOKIE_READ_KEY` 时仅允许服务器本机回环调用，并要求客户端地址与 `Host` 同时为回环地址；非回环调用必须使用 HTTPS。反向代理传递的 `X-Forwarded-For` 只取最后一跳地址，不信任客户端可伪造的前缀。
- 接口按来源限流，成功审计事件按来源合并，审计映射设有硬上限并保留最近记录；审计与日志只记录时间、结果和去标识化来源，不记录 Cookie 内容。
- 响应设置 `Cache-Control: no-store` 与 `x-robots-tag`，缺少可用登录态时返回 `503`；全部登录态处于临时隔离期时返回 `200` 且 `quarantined` 为 `true`，调用方应视为可能失效。
- 该响应等同于微博登录态，任何持有者都可能以对应账号身份操作。运营者只应向确有必要的受信服务提供，并在启用后把接收方写入 `dataRecipientDisclosure`。

## 已确认的边界

- 前端仅连接预配置地址或本机地址。备用 Cookie 和官方访问令牌只用于当前任务，任务结束后清除。
- 后台使用 scrypt 密码哈希、签名会话、HttpOnly/Secure/SameSite Cookie、CSRF 校验、登录限流和并发密码校验上限。
- JSON 请求、微博响应、头像、候选、奖项、中奖人、反馈和开奖记录均有容量或数量限制。
- 头像代理只允许微博与新浪图片域名，禁止重定向，并限制类型、大小、并发和缓存。
- 同一微博的并发载入会共享任务，短时复用完成快照；队列、单来源任务、订阅者、执行时间和完成响应体积均有上限。
- 微博入口返回不完整时会补扫备用入口；连续空页和重复页会提前停止。失效 Cookie 会轮换到下一条可用登录态。
- Cookie 统计区分已保存、可尝试、已验证、待验证、校验异常和临时隔离；被隔离的登录态不会同时计入当前已验证数量。
- 后台动态内容在写入 HTML 前统一转义，外链经过微博域名白名单。
- 服务端 CSP 禁止第三方脚本、内联脚本属性、框架嵌入和对象加载。
- systemd 让 Node 仅监听回环地址，限制内存、任务数和可写目录，并按日回收进程。Chromium 超时后会关闭上下文、终止确属当前 Profile 的残留进程并清理可再生成缓存。
- 导入损坏的开奖记录备份、空响应和旧版字段均按空对象归一化，不会因 `null` 或非对象输入中断界面；跨标签页写入使用事务锁，手动名单开奖后“排除已中奖用户”不会被无关状态更新清空。

## 产品与部署边界

- 公开的开奖记录保存接口允许客户端提交内容。过程哈希用于复查随机过程，不是不可伪造的第三方证明。
- “排除已中奖用户”和一分钟开奖间隔属于当前浏览器、当前任务的操作保护，不是跨设备的活动身份系统。
- 公开 API 仍可能遭遇分布式流量；应用内限流和资源上限保护单机，大规模攻击仍需云防火墙或 CDN/WAF。
- 生产环境必须使用独立且足够长的 `ADMIN_SESSION_SECRET`、`COOKIE_WRITE_KEY`、`COOKIE_READ_KEY` 和来源指纹密钥，并让 Node 只监听 `127.0.0.1`。
- 生产环境默认启用 Chromium 沙箱（`WEIBO_BROWSER_SANDBOX=1`）。上线前仍须在目标服务器以真实 `www-data + systemd` 约束验证 Playwright、字体缓存、Profile 权限和退出后的进程清理；只有确认内核不支持时才可显式关闭。
- 服务器发布默认拒绝脏工作树，并从明确的 Git commit 生成归档；发布目录记录 `.release-commit`，未提交和未跟踪文件不会混入制品。非 Git 离线包必须显式启用例外开关。
- GitHub Pages 只能通过 HTML meta 下发部分 CSP；服务器托管版使用完整响应头。
- CSP 的 `style-src` 保留 `'unsafe-inline'` 以兼容 React 动态样式和后台图表；脚本策略不允许 `'unsafe-inline'` 或 `'unsafe-eval'`。
- 正式安装脚本在部署前执行 `npm run legal:check`，任一法律配置字段为空或仍是占位内容时拒绝部署。仓库内头像、偶像图片和摄影等素材未记录外部来源与授权证明，公开上线前必须由运营者逐项确认并留存权利证明。

# 可新增与可优化方向

这份清单是发散用的，不是待办承诺。每条都写了「现在是什么样、可以往哪走、
值不值得、代价在哪」，决定要做的再拆成具体任务。标注里的成本指大致投入：
小 = 一两天量级，中 = 一周量级，大 = 需要新架构或外部依赖。

## 怎么挑

先看三件事：用户能不能感知、坏了会不会让抽奖不可用、有没有外部依赖。
外部依赖越多（微博之外的平台、第三方服务、证书服务），越应该放到后面。

## 一、抽奖展示（够用就行）

这不是专业抽奖平台，目标只是让结果看起来公正、说得清楚，不是给陌生人提供一套
可验证随机数协议。现在的实现已经有 `seed`、候选摘要、`auditHash`、开奖前确认
弹层、结果图上的算法说明和可复制的公平性文案，这条线可以就此打住。

| 方向 | 现在 | 可以做成 | 成本 |
| --- | --- | --- | --- |
| 规则说明更直白 | 结果弹层有算法与规则摘要 | 用一两句人话写清「候选怎么来的、怎么抽的、为什么不可复现」 | 小 |
| 结果图展示校验码 | 结果图有算法说明 | 把 `auditHash` 短码放在结果图角落，作为「可核对」的视觉信号 | 小 |
| 开奖前确认页 | 已有确认弹层 | 保持现状，别再加流程 | - |

明确不做：commit-reveal、哈希链账本、独立复验页、随机性统计检验、过程回放。
这些是给专业抽奖平台做的，投入大、没人看，还会把开奖流程弄复杂。

## 二、候选抓取与筛选

现在的筛选是关键词、@ 人数、排除名单、去重、排除已中奖五项，够用但不细。

| 方向 | 说明 | 成本 |
| --- | --- | --- |
| 多次转发加权 | 现在同一用户只保留一条；可增加「按转发次数加权」和「取最早/最新一条」策略 | 小 |
| 筛选预设可保存 | 现在只有三个固定预设，可以做成自定义预设，本地保存并可分享 | 小 |
| 黑名单沉淀 | 从结果里一键把某人加入排除名单，跨任务保留，可导入导出 | 小 |
| 名单导入格式扩展 | 现在粘贴文本，可支持 CSV/Excel/JSON 与字段映射（uid、昵称、链接） | 中 |
| 增量续抓 | 任务结束后保留快照指纹，下次只补新增转发（已有 15 秒快照缓存可复用） | 中 |
| 资格规则增强 | 注册时间、粉丝数、是否带图、是否原创等，取决于微博接口能拿到多少字段 | 中 |
| 身份归一策略 | UID 优先、昵称兜底，处理改名和重名；让去重规则可见可控 | 中 |
| 多平台候选 | 把抓取抽象成 provider 接口，未来接 B 站、抖音、小红书转发数据 | 大 |

多平台是唯一一个会改变项目定位的方向，值得单独评估，不要顺手做。

## 三、开奖现场与结果表达

这是最容易让用户「觉得好用」的一块。

| 方向 | 说明 | 成本 |
| --- | --- | --- |
| 大屏/投屏模式 | 全屏、放大字号、隐藏导航，适合直播或连麦现场 | 小 |
| 动画时长与音效 | 现在只有完整/跟随系统/减少，可加时长档位、倒计时、可选音效 | 小 |
| 多轮编排 | 一次活动分多轮，轮次绑定结果并自动排除前几轮中奖者（现有单任务排除可复用） | 中 |
| 分层抽奖 | 按规则分池（老粉/新粉、地区、粉丝量段），各池独立名额 | 中 |
| 结果图模板 | 多套模板，可选是否显示头像/UID/时间，支持水印 | 中 |
| 公告模板扩展 | 更贴近微博转发抽奖的公告格式，带话题、链接、@ 列表 | 小 |
| 结果页分享 | 生成只含结果（不含候选数据）的分享链接或图片，方便发到微博 | 中 |

## 六、性能与架构

当前首屏约 125 KB（压缩后），慢速 4G 加降速 CPU 下约 1.35 秒可见，没有必要时
为了体积做大改造。下面几条是收益明确的：

| 方向 | 说明 | 成本 |
| --- | --- | --- |
| 进度推送替代轮询 | 现在任务进度 700 毫秒轮询一次；换成 SSE 可降请求数、提高即时性，注意代理超时 | 中 |
| 存储换 SQLite | 现在记录、反馈、事件都是 JSON 文件；数据量上来后查询和并发会更稳 | 大 |
| 长列表虚拟化 | 候选上限 2 万条，全部渲染会卡；只渲染可视区域 | 中 |
| 静态资源空闲预取 | 首页空闲时预取结果图与法律文本分包 | 小 |
| 头像代理优化 | 按尺寸请求、命中率统计、失败兜底头像 | 小 |
| 前端性能监测 | 自建、无第三方，把首屏指标回传到后台 | 中 |

## 七、安全与合规

原则：不要为了安全把公开前端搞成不可用，真正要守的是注入、鉴权、登录态和
服务端出站请求。

| 方向 | 说明 | 成本 |
| --- | --- | --- |
| 密钥策略收敛 | 公开部署不加密钥（已改默认），私有部署可选；文档写清两种模式不能混 | 小 |
| 隐藏真实服务地址 | 设置页默认只显示「已使用预置服务地址」，需要手填本机或自建地址时才出现输入框（已改） | 已完成 |
| 后台入口改名 | 支持 `ADMIN_BASE_PATH`，把 `/admin` 换成不好猜的路径，前端不链接后台（已改） | 已完成 |
| 数据自助删除 | 用户可一键删除本机记录；服务器侧按保留策略自动过期（已有） | 小 |
| 法律文案对齐 | 已按当前部署要求固定为服务器位于美国怀俄明州 | 已完成 |
| 素材授权闭环 | 按 `docs/ASSET-NOTICES.md` 逐项确认或替换素材 | 小 |
| 出站请求白名单 | 现在有 SSRF 防护；可把允许的出站域名集中成一处配置 | 小 |

## 九、不建议做

- 不碰「预测中奖」「自动 @ 中奖者代发微博」：触发平台风控，收益低风险高。
- 不做需要微博账号密码的功能：只走官方授权或本机 Cookie。
- 不为概念引入外部依赖：区块链存证、第三方分析、外部队列，收益都撑不住成本。
- 不为「看起来智能」加 AI 功能：这个工具要的是可复验和稳定，不是话术。

## 十、如果要排优先级

先做这些：筛选预设保存、黑名单沉淀、大屏模式、公告模板扩展和数据自助删除。
共同点是成本小、用户直接感知、不引入新依赖。

再评估：多轮编排、弱网容错、队列可视化、SSE 进度、长列表虚拟化。

最后才是：多平台候选、SQLite 迁移、分层抽奖。这三项都会改变项目结构，应该
单独设计方案并先做兼容验证。

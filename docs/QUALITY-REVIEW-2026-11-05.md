## 本轮修复

### 开奖次数的异步归属

复现顺序为：输入微博链接、发起次数查询、载入候选返回次数 9，再释放较早的查询返回 2。
旧实现显示了 2，覆盖了更新的载入结果。修改访问密钥也不会触发重新查询。
失败证据位于 `output/quality-20261105/draw-count-before.log`。

`useDrawCount` 统一管理来源、链接、后端地址与访问密钥对应的次数、请求和防抖计时器。
上下文改变时立即失效旧查询；读取响应正文后仍检查请求所有权。候选载入和正式保存返回
次数时取消旧查询与尚未执行的防抖任务，卸载时一起清理。

`test-draw-count-ui.mjs` 通过真实页面交互覆盖：旧查询晚于载入、修改密钥、切换有效链接、
改为无效链接、切换后端、快速载入取消防抖，以及正式保存后旧查询晚到。
保存场景继续打开下一次开奖确认，检查实际使用的历史次数，避免只检查结果页固定文案。
次数仍只接受非负安全整数，未知值不转换为零。

### 静态响应的编码协商

客户端明确发送 `identity;q=1, gzip;q=0.2` 时，旧实现仍返回 gzip。新增测试先失败，
修复后通过。现在明确给出的未压缩响应权重参与排序，未指定时保留可接受的回退行为；
禁止所有可用编码仍返回 406。同等权重保留压缩优先。
单元测试覆盖编码可用性和优先级，HTTP 集成验证实际响应头与未压缩正文一致。

## 性能测量

新增 `test-large-list-ui.mjs`，使用 20,000 条虚构候选。首批只渲染 20 条，搜索能够找到
最后一位候选；关键词筛选得到 10,000 条可抽与 10,000 条排除，完整名单没有因分批显示截断。
测试输出测量值，但不采用易受机器负载影响的毫秒级硬阈值。

本机 Chrome、390 × 844、禁用缓存、4 倍 CPU 降速、减少动效、无网络降速的一次样本：

| 指标 | 结果 |
| --- | --- |
| 首屏 LCP / CLS | 592 ms / 0 |
| 首批公开资源响应体 | 147,945 字节，约 144.5 KiB（含图标，不含响应头） |
| 载入两万条候选 | 461 ms |
| 搜索名单最后一位 | 91 ms |
| 应用关键词筛选 | 279 ms |
| 最终 DOM 元素 / JS 堆 | 515 / 约 20.4 MiB |
| 最大长任务 | 294 ms，出现在首屏初始化 |

操作耗时从浏览器时钟记录自动操作开始至界面断言完成，包含自动化开销；候选接口由本机
夹具返回，不包含真实微博抓取时间。这些是实验室样本，不是线上 Web Vitals 或实体手机承诺。
证据：`output/quality-20261105/large-list-cpu4.log`。

当前压力检查中，服务在预热后执行六轮各千次请求，RSS 从 67.8 MiB 到 77.8 MiB、
JS 堆从 11.7 MiB 到 11.4 MiB，限流桶保持在 120 的上限内。四轮独立浏览器启停后，
JS 堆从 19.0 MiB 到 19.3 MiB；两项检查结束时各自的 Chromium 进程计数均为 0。
这些有界压力检查验证回收和容量约束，不代表任意运行时长都没有泄漏。
